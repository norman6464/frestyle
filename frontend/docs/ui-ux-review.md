## 方針

- 大きな一覧を一律にカード化せず、主情報と補助情報を分ける。
- スマートフォンでは折り返し、主要操作を44px以上にする。長い名前や深い階層を確認する。
- 認証や編集権限の判定は既存の処理を使う。存在しない機能やAPIは追加しない。
- 更新・削除などの書き込みはユーザー操作時のみ。Storybookはモックデータで検証する。
- 開発用UIカタログは製品画面とは別扱いとし、共通部品の互換性を確認する。

- 全ユニットテスト：164ファイル・1,747件が成功。
- 対象画面・共通部品のStorybookブラウザテスト：106ファイル・526件が成功（アクセシビリティ検査を含む）。

- 最終の17画面×3サイズでは意図しない横はみ出しなし。状態・種別の管理表だけは、ラベル付きの領域内で横スクロールする。
- 実ブラウザで、モバイルメニューの初期フォーカス、Tab循環、Escape、起点へのフォーカス復帰を確認。コメントパネルの開閉と共有パネルの画面内への収まりも確認。

| 画面 | 変更 |

## Skillsの適用範囲

UI/UX Pro Maxの既存画面向け手順とui-stylingを使用。既存トークンと共通部品を優先し、情報の優先順位・操作対象・フォーカス・状態別の導線に反映した。この段階では新しい配色、外部画像、依存ライブラリは追加していない。ローカル検索で段階的な操作表示に適合する結果は得られなかったため、その部分はSkills本文と実画面の検証で判断した。後続のBase UI導入とDS定義は [design-system.md](./design-system.md) を参照。

## 共通基盤と主要画面の再構成（追加）

スクリーンショットへのフィードバックを受け、色ではなく「次に行う作業」と「補助操作」の優先順位を変更した。既存の部品を一律に置き換えず、APIの互換性と権限判定を維持しながら画面を再構成している。

| 対象 | 今回の変更 |
| --- | --- |
| 共通UI | `PageFrame` で作業・読書・フォームの幅を分ける。`ContentSection` で領域の見出し・説明・操作をまとめ、`Disclosure` で補助操作を段階表示する。ボタンはPCの密度とタッチ操作を分け、影への依存を減らす |
| ホーム | リンクカード中心から、実データの未完了担当チケットを最大5件表示する構成へ。期限超過→今日が期限→進行中の順。最近見たナレッジは副列に置く。件数は取得結果から計算し、一部失敗・全失敗・空を区別する |
| チケット詳細 | 本文と属性を単一のスクロール領域内の左右2列へ。狭い画面では担当・期限の概要を本文の前、編集可能な詳細を下段へ置く。属性の長い未設定案内を短縮し、読み取り専用では「設定」を促さない |
| バックログ | 最大幅を設定し、識別子・題名・補足を分ける。担当者はアバターだけでなく名前も表示。状態の入力枠は中立色に統一し、題名を開く操作と状態変更を分離する |
| ナレッジ | コメント・提案・共有は常時表示。履歴・テンプレート・カバー・アイコンは「ページの設定とその他の操作」にまとめ、タイトルと本文を優先する |
| 操作名 | ヘッダーは実際の機能に合わせて「移動先を探す」、ナレッジの検索は「ナレッジ内を検索」。Dexのログイン入口は「ログイン画面へ進む」として画面遷移を明示 |

### 共通部品の利用方針

- `PageFrame` は幅と余白のみを持ち、スクロール管理や業務ロジックを持たない。既定の `workspace` は一覧・作業画面、`reading` は読書、`form` は入力画面向け。
- `ContentSection` は見出し付きの領域であり、すべての一覧行をカードにするための部品ではない。
- `Disclosure` は通常のボタンとTab順を使う。開閉状態を `aria-expanded` で伝え、Escapeで閉じて起点にフォーカスを戻す。閉じても子をアンマウントせず、入力状態を保持する。
- `ui-control` / `ui-control-compact` は、通常のポインターでは40px / 32px、タッチ主体のポインターでは44px以上を確保する。
